# **1\. Введение**

## **1.1. Назначение**

Настоящий документ определяет требования к мобильному приложению «Запись на приём», предназначенному для пациентов сети медицинских клиник.

Документ устанавливает функциональные и нефункциональные требования к программному обеспечению, интерфейсам, данным, ограничениям и условиям эксплуатации приложения.

SRS предназначен для использования:

* заказчиком;  
* системными и бизнес-аналитиками;  
* разработчиками;  
* тестировщиками;  
* UI/UX-дизайнерами;  
* специалистами по сопровождению системы.

## **1.2. Область применения**

Программный продукт представляет собой мобильное приложение, предоставляющее пациенту возможность самостоятельно взаимодействовать с системой записи на приём.

Приложение должно обеспечивать:

* просмотр списка медицинских специализаций;  
* поиск и просмотр врачей;  
* просмотр расписания врачей;  
* запись на приём;  
* просмотр предстоящих записей;  
* перенос записи;  
* отмену записи;  
* получение уведомлений;  
* просмотр истории посещений.

Приложение не должно предоставлять пациенту возможность:

* изменять медицинскую документацию;  
* редактировать данные о врачах;  
* изменять расписание врачей;  
* просматривать медицинские карты других пациентов.

## **1.3. Определения, акронимы и аббревиатуры**

**Пациент** \- пользователь мобильного приложения, который записывается к врачу.

**Врач** \- медицинский специалист, доступный для записи.

**Специализация** \- профиль работы врача.

**Запись** \- дата и время, когда пользователь записан к врачу.

**Временной интервал** \- период времени для создания записи к врачу.

**МИС** \- медицинская система клиники.

**API** \- Application Programming Interface, программный интерфейс, который позволяет одной компьютерной программе общаться с другой или использовать ее функции.

**SRS** \- Software Requirements Specification.

**MVP** \- минимальная жизнеспособная версия продукта.

## **1.4. Ссылки**

Основным нормативным документом при подготовке настоящей спецификации является:

**ISO/IEC/IEEE 29148:2018 — Systems and software engineering — Life cycle processes — Requirements engineering.**

Стандарт определяет процессы разработки требований, содержание соответствующих информационных элементов и рекомендации по формулированию требований.

# **2\. Обзор**

## **2.1. Краткое описание продукта**

Мобильное приложение является клиентской частью информационной системы сети медицинских клиник.

Упрощенная схема взаимодействия:

**Пациент → Мобильное приложение → API сервера → МИС клиники**

Дополнительно приложение взаимодействует с:

* сервисом push-уведомлений;  
* системой аутентификации;  
* мобильной операционной системой.

Мобильное приложение не является источником данных о расписании врачей. Актуальное расписание должно предоставляться серверной частью системы.

## **2.2. Функции продукта**

Основные функции продукта:

1. Авторизация пациента.  
2. Регистрация пациента.  
3. Восстановление пароля.  
4. Просмотр специализаций.  
5. Просмотр списка врачей.  
6. Поиск врача.  
7. Просмотр информации о враче.  
8. Просмотр расписания.  
9. Создание записи.  
10. Просмотр активных (т.е. предстоящих) записей.  
11. Перенос записи.  
12. Отмена записи.  
13. Получение уведомлений.  
14. Просмотр истории посещений.

Приложение должно предоставлять следующие основные экраны:

* экран авторизации;  
* экран регистрации  
* главный экран с записями пациента;  
* список специализаций;  
* список врачей;

* расписание;

Основная навигация приложения должна обеспечивать переход между разделами без необходимости повторной авторизации пользователя.

## **3.2. Интерфейс программы**

Приложение должно взаимодействовать с серверным API для:

* получения списка специализаций;  
* получения списка врачей;  
* получения расписания;  
* создания записи;  
* изменения записи;  
* отмены записи;  
* получения истории посещений.  
* создания аккаунта пациента.  
* изменения данных аккаунта пациента.

Приложение должно взаимодействовать с системой push-уведомлений для доставки уведомлений пациенту.

# **4\. Функциональные требования**

Каждое требование имеет уникальный идентификатор.

## **4.1. Авторизация пользователя**

### **FR-AUTH-001. Ввод данных для авторизации.**

**Описание:** Система должна предоставлять пациенту возможность ввести номер телефона или почту, а также пароль для авторизации.

### **FR-AUTH-002. Успешная авторизация. Вывод главного экрана.**

**Описание:** После успешной проверки введенных данных система должна показывать пользователю окно Главного экрана со списком его активных (т.е. предстоящих) записей к врачу.

### **FR-AUTH-003. Ошибка авторизации.**

**Описание:** Система должна выводить сообщение об ошибке, если данные авторизации не соответствуют тем, что хранятся на сервере.

### **FR-AUTH-004. Восстановление пароля.**

**Описание:** Пользователь должен иметь возможность восстановить доступ к аккаунту, введя почту, к которой привязан аккаунт. Система должна проверить, есть ли аккаунт с такой почтой и отправить на нее одноразовый код.

## **4.2. Регистрация пользователя**

### **FR-REG-001. Ввод данных для регистрации.**

**Описание:** Пользователь должен иметь возможность зарегистрироваться в системе, введя следующие данные:

* ФИО  
* Дата рождения  
* Email  
* Телефон  
* Пароль  
* Подтверждение пароля

### **FR-REG-002. Длина пароля.**

**Описание:** Система должна отклонять пароль при регистрации, если его длина составляет менее 7 или более 50 символов. 

### **FR-REG-003. Необходимые символы пароля.**

**Описание:** Система должна отклонять пароль при регистрации, если он не содержит хотя бы один символ из набора \!, @, \#. 

### **FR-REG-004. Подтверждение аккаунта одноразовым кодом.** 

**Описание:** Система должна запрашивать проверку аккаунта пользователя одноразовым кодом при регистрации. 

### **FR-REG-005. Создание и отправка одноразового кода регистрации.**

**Описание:** Одноразовый код должен генерироваться самой системой и отправляться на указанную пользователем почту.

## **4.3. Личный кабинет пациента**

### **FR-PROF-001. Просмотр данных профиля пациента**

**Описание:** Система должна предоставлять пациенту возможность просматривать данные своего профиля.

### **FR-PROF-002. Изменение данных профиля**

**Описание:** Система должна предоставлять пациенту возможность изменять разрешённые для редактирования данные \- телефон, почту, пароль.

### **FR-PROF-003. Настройки уведомлений**

**Описание:** Система должна предоставлять пациенту возможность изменять настройки уведомлений.

## **4.4. Специализации**

### **FR-SPEC-001. Список специальностей.**

**Описание:** Система должна предоставлять пользователю список всех специальностей врачей во всех клиниках.

### **FR-SPEC-002. Список врачей.**

**Описание:** Пользователь должен иметь возможность просмотреть список врачей конкретной специальности, кликнув на нужную.

### **FR-SPEC-003. Поиск врача по списку.**

**Описание:** Пользователь должен иметь возможность произвести поиск врача, введя название специализации или ФИО врача в поле поиска.

## **4.5. Врачи**

### **FR-DOC-001. Список врачей.**

**Описание:** Система должна предоставлять пользователю список всех врачей выбранной специальности. Если у врача несколько специальностей, то он должен выводиться в списках всех специальностей.

### **FR-DOC-002. Карточка врача в списке.**

**Описание:** Система должна выводить краткую информацию о каждом враче в списке всех врачей нужной специальности:

* ФИО  
* Специальности  
* Стаж  
* Адрес клиники, в которой работает врач  
* Цена за консультацию  
* Свободные слоты расписания для записи на прием.

### 

### **FR-DOC-003. Страница врача.**

**Описание:** Система должна показывать страницу врача со следующими параметрами:

* ФИО.  
* Специальности.  
* Стаж.  
* Блок расписания и записи на прием (см. раздел 4.6).  
* Образование.

## **4.6. Расписание и запись на прием**

### **FR-APNT-001. Выбор клиники.**

**Описание:** Система должна предоставлять возможность выбрать клинику, в которой работает врач, для последующего обращения. От этого выбора должны меняться:

* Специальность врача, которую можно выбрать.  
* Цена за прием.  
* Номер телефона.

### **FR-APNT-002. Выбор специальности врача для записи.**

**Описание:** Система должна предоставить пользователю возможность выбрать, по какой из специальностей обратиться к выбранному врачу.

### **FR-APNT-003. Расписание. Даты.**

**Описание:** Система должна выводить расписание врача на ближайший месяц. Месяц должен рассчитываться, начиная с текущего дня \+ 30 дней вперед.

### **FR-APNT-004. Расписание. Время.**

**Описание:** Система должна выводить свободное время для записи для выбранной пользователем даты. Временные слоты не должны быть привязаны к специальности, но должны быть привязаны к клинике. Если у врача занято время в одной клинике, то в другой клинике это же время на эту же дату также должно быть занято.

### **FR-APNT-005. Повторная запись на прием.**

**Описание:** Пациент должен иметь возможность повторно записаться на прием, просматривая карточку записи из истории посещений (см. раздел 4.9).

### 

### **FR-APNT-006. Просмотр активной записи.**

**Описание:** Пациент должен иметь возможность просмотреть данные активной записи (т.е той которая еще не прошла). Система должна вывести следующие данные:

* Дата и время  
* ФИО врача  
* Специализация врача  
* Адрес и название клиники, в которой будет проходить прием  
* ФИО пациента  
* Предварительная цена за прием  
* Статус записи (активная)

## **4.7. Перенос записи на прием**

### **FR-CHAPNT-001. Перенос записи.**

**Описание:** Пациент должен иметь возможность перенести запись на прием на любые другие свободные даты и время.

### **FR-CHAPNT-002. Ограничение переноса.**

**Описание:** Пациент не должен иметь возможность перенести уже прошедшую запись.

## **4.8. Отмена записи на прием**

### **FR-CANAPN-001. Отмена записи.**

**Описание:** Пациент должен иметь возможность отменить запись на прием на любые другие свободные даты и время. 

### **FR-CANAPN-002. Слот времени записи.**

**Описание:** Система должна “разблокировать” для записи тот слот времени, от которого отказался пациент.

### **FR-CANAPN-003. Ограничение отмены.**

**Описание:** Пациент не должен иметь возможность отменить уже прошедшую запись.

## **4.9. Уведомления**

### **FR-NAPNT-001. Уведомление пользователя после создания записи.**

**Описание:** Как только пациент создаст запись на прием, то система должна отправить на телефон пользователя push-уведомление с напоминанием и данными записи к врачу, а также призывом подготовиться к приему. 

### **FR-NAPNT-002. Уведомление пользователя за день, за 5 часов и за час до приема.**

**Описание:** Система должна отправлять push-уведомления с напоминанием о записи к врачу за день до, за 5 часов и за час до приема.

### **FR-NAPNT-003. Уведомление пользователя после переноса приема.**

**Описание:** Система должна отправлять push-уведомления об успешном переносе приема.

### **FR-NAPNT-004. Уведомление пользователя после отмены приема.**

**Описание:** Система должна отправлять push-уведомление об успешной отмене приема.

### **FR-NAPNT-005. Сообщения об ошибке.**

**Описание:** Система должна выводить сообщения об ошибке в случаях, описанных в 5.4

## **4.10. История посещений**

### **FR-HSTR-001. История посещений.**

**Описание:** Система должна сохранять всю историю посещений и выводить ее в человеко-читаемом варианте.

### **FR-HSTR-002. Данные по прошедшему приему в списке истории.**

**Описание:** Система должна выводить следующую краткую информацию в истории посещений:

* Дата и время  
* ФИО врача  
* Специализация врача

### **FR-HSTR-003. Полные данные записи к врачу.**

**Описание:** Система должна выводить следующую информацию на странице записи к врачу:

* Дата и время  
* ФИО врача  
* Специализация врача  
* Итоговая оплата  
* Статус записи  
* Опция повторной записи

# **5\. Нефункциональные требования**

## **5.1. Требования к эксплуатации**

### **NFR-PERF-001. Отображение данных после отправки запроса.**

**Описание:** При нормальном сетевом соединении система должна отображать основные данные экрана не более чем через 3 секунды после отправки запроса.

### **NFR-PERF-002. Получение ответа от сервера.**

**Описание:** При создании записи система должна возвращать результат операции не более чем через 5 секунд после подтверждения пациентом при доступности серверной системы.

## **5.2. Требования к безопасности**

### **NFR-SEC-001. Защита персональных данных.**

**Описание:** Система должна передавать персональные данные пациента по защищённому соединению.

### **NFR-SEC-002. Доступ к данным пациента.**

**Описание:** Система должна предоставлять пациенту доступ только к данным, связанным с его учётной записью.

### **NFR-SEC-003. Запрет на доступ к данным других пациентов.**

**Описание:** Система не должна отображать пациенту персональные данные других пациентов.

### **NFR-SEC-004. Шифрование.**

### **Описание:** Данные авторизации пациента должны быть зашифрованы. Алгоритм шифрования может быть определен разработчиками, исходя из возможностей системы.

## **5.3. Требования к удобству использования**

### **NFR-USE-001. Переход к созданию записи.**

**Описание:** Система должна предоставлять возможность перейти от выбора врача к сценарию записи как из списка врачей, так и со страницы конкретного врача.

### **NFR-USE-002. Расписание. Даты отсутствия/полной занятости врача.**

**Описание:** Если дата уже вся расписана на приемы или врача не будет на месте (например, в отпуске), то система должна отразить это в расписании.

## **5.4. Требования к надежности**

### **NFR-REL-001. Потеря соединения с сервером.**

**Описание:** При потере соединения с сервером система должна уведомить пациента о невозможности выполнить операцию.

### **NFR-REL-002. Ошибка создания/переноса/отмены записи.**

**Описание:** Если при создании, переносе или отмене записи произошла ошибка, то система не должна отображать запись как созданную, перенесенную или отмененную. Уведомления о создании, переносе и/или отмене не должны отправляться.

### **NFR-REL-003. Дубликаты записи.**

**Описание:** Повторная отправка одного запроса на создание записи не должна приводить к созданию нескольких одинаковых записей.

# **6\. Требования к данным**

## **6.1. Пациент**

Система должна поддерживать следующие данные пациента:

* ФИО  
* Дата рождения и возраст  
* Телефон  
* Email  
* Пароль  
* Статус аккаунту (активный/неактивный)

## **6.2. Врач**

Система должна поддерживать следующие данные врача:

* ФИО  
* Специальности  
* Клиника, в которой врач работает  
* Стаж  
* Актуальное расписание  
* Образование  
* Цены за прием по каждой специальности в каждой клинике  
* Номер телефона врача

## **6.3. Запись**

Система должна поддерживать следующие данные записи:

* Дата и время  
* ФИО врача  
* Специализация врача  
* Адрес и название клиники, в которой будет проходить прием  
* ФИО пациента  
* Итоговая оплата  
* Статус записи (активная/прошедшая)

# 

# **7\. Бизнес-правила и ограничения**

## **BR-001. Назначение времени записи**

**Описание:** Один временной интервал не может одновременно быть назначен двум пациентам.

## **BR-002. Создание записи**

**Описание:** Пациент может создать запись только на доступный временной интервал.

## **BR-003. Перенос записи**

**Описание:** Перенос записи возможен только при наличии нового доступного временного интервала.

## **BR-004. Отмена записи**

**Описание:** Отменить можно только активную запись, которая ещё не завершена и не была отменена.

## **BR-005. Наполнение истории посещений**

**Описание:** Завершённые посещения должны отображаться в истории посещений.

## **BR-006. Актуализация свободного времени**

**Описание:** Актуальность свободного временного интервала должна проверяться серверной системой непосредственно перед созданием или переносом записи.

**BR-007. Срок отмены и переноса записи**

**Описание:** Правила допустимого срока отмены и переноса записи определяются правилами сети медицинских клиник.

# **8\. Критерии приемки MVP**

MVP считается соответствующим требованиям, если успешно пройдены тесты для следующих сценариев:

1. Авторизация пациента.  
2. Выбор специализации.  
3. Просмотр списка врачей.  
4. Просмотр карточки врача.  
5. Просмотр расписания.  
6. Создание записи.  
7. Просмотр активной записи.  
8. Перенос записи.  
9. Отмена записи.  
10. Получение уведомлений.  
11. Просмотр истории посещений.  
12. Просмотр Личного кабинета.  
13. Изменение данных ЛК.

Для каждой операции с записью должна выполняться проверка актуальности данных на сервере.

# **9\. Прослеживаемость**

Для обеспечения трассируемости требований каждому требованию присвоен уникальный идентификатор. 

# **10\. Будущие нововведения**

Следующие возможности не входят в текущий MVP, но могут быть рассмотрены в последующих версиях:

* Авторизация и регистрация через аккаунт Госуслуг, Yandex, VK.  
* Авторизация с помощью отпечатка пальцев  
* Полноценный личный кабинет пациента  
* Проверка документов врача  
* Рейтинги и отзывы врача  
* Медкарта  \- загрузка результатов приема, анализов, данных из Госуслуг  
* Трекер менструального цикла  
* Промокоды/скидки  
* Возможность записи члена семьи (т.е. не хозяина аккаунта а его родственника/друга)  
* Статистика по посещениям, отзывам  
* Онлайн-оплата  
* Удаление аккаунта
